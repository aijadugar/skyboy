# Skyboy Skill Spec

The canonical format a skyboy.in skill package follows. This is the portable
Anthropic Agent Skills structure, extended with a skyboy-specific metadata sidecar
so we never pollute the standard format with our own fields.

## 1. Skill package layout

```
skill-name/
  SKILL.md          # REQUIRED - YAML frontmatter + markdown instructions
  scripts/          # optional - executable helpers (python/js/bash)
  references/       # optional - docs loaded on demand (progressive disclosure)
  assets/           # optional - templates, boilerplate, static files
  metadata.json     # skyboy-specific: category, tags, agents, license, author
```

The one file that must always exist is `SKILL.md`. Everything else is optional.

### `SKILL.md` frontmatter (minimum viable)

```yaml
---
name: nextjs-app-router-conventions
description: Use when scaffolding or reviewing Next.js App Router projects. Enforces routing, data-fetching, and folder-structure conventions.
---
```

The **name + description** is what agents scan cheaply (dozens of tokens) before
deciding to load the full body. Description quality is the single highest-leverage
field in the whole schema. Bad descriptions = skill never triggers, no matter how
good the body is.

Recommended additional frontmatter:

```yaml
---
name: nextjs-app-router-conventions
description: Use when scaffolding or reviewing Next.js App Router projects. Enforces routing, data-fetching, and folder-structure conventions.
license: MIT
compatible_agents: [claude-code, claude-desktop, cursor, gemini-cli]
---
```

## 2. `metadata.json` schema (skyboy-specific)

This is separate from `/the portable SKILL.md` so we don't pollute the standard
format. It is the machine-readable record the site, MCP server, CLI, and CI all
read.

```json
{
  "category": "coding/frontend",
  "tags": ["nextjs", "react", "app-router"],
  "compatible_agents": ["claude-code", "claude-desktop", "cursor", "gemini-cli"],
  "license": "MIT",
  "author": "github-handle",
  "verified": false,
  "version": "1.0.0",
  "permissions": {
    "network": false,
    "filesystem_write_outside_target": false,
    "shell_exec": false,
    "env_read": [],
    "generated_by": "generate-manifest.ts@1.0.0",
    "generated_at": "2026-09-02T00:00:00Z"
  },
  "canonical_of": null
}
```

### Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `category` | string | yes | Exactly one primary category from the taxonomy tree. |
| `tags` | array | yes | Up to 3 tags, plus the category. |
| `compatible_agents` | array | yes | Agent slugs the skill is known to work with. |
| `license` | string | yes | `MIT` default; CI fails on absence. |
| `author` | string | yes | GitHub handle or org. |
| `verified` | boolean | yes | `false` until maintainer review (badge assignment). |
| `version` | string | yes | Semver. Drives the "diff view on updates" feature. |
| `permissions` | object | generated | Machine-generated; must not be hand-edited (see `docs/skill-spec.md` §4). |
| `canonical_of` | string/null | yes | `null` for canonical; else the slug this entry duplicates (§5). |

### Taxonomy

See `skills/` directories. Browse is flat by category + up to 3 tags, not deep
nested browsing (fastest path).

## 3. Permissions manifest contract

`permissions` is machine-generated by `scripts/generate-manifest.ts` (CI, §12.1
of the build brief) via static analysis of any bundled scripts. It is a
**disclosure, not a gate**: a skill that needs network access or shell exec is
fine, it just has to say so.

| Key | Type | Meaning |
|---|---|---|
| `network` | boolean | Any outbound HTTP/socket call in a bundled script. |
| `filesystem_write_outside_target` | boolean | Writes beyond the skill's own folder or the agent's declared target directory. |
| `shell_exec` | boolean | `exec`/`spawn`/`eval`/subprocess calls in a bundled script. |
| `env_read` | array | `process.env` / `os.environ` access, esp. secret-named (`*_KEY`, `*_TOKEN`, `*_SECRET`). |
| `generated_by` | string | The tool + version that produced it. |
| `generated_at` | timestamp | When it was regenerated. |

**Rule:** CI fails the build only when a script does something **undisclosed**
relative to what the contributor's PR description said the skill does - exactly
the "fail on undisclosed network/eval/credential access, not on those capabilities
being present" framing in §11/§12.1 of the build brief.

## 4. Content types

A catalog entry is either a standalone **Skill** (this spec) or a **Plugin**
(§3.1 of the build brief) - a bundle of `commands/`, `agents/`, `hooks/`, one or
more `skills/`, and optionally an `.mcp.json`. Plugins are indexed + linked back
to the vendor repo as the source of truth (never vendor-copied), and carry an
`official (vendor)` badge. The Skill-vs-Plugin distinction is a **search facet**,
not a different underlying format.

## 5. Deduplication / canonical version

`canonical_of` points a duplicate/alternate entry at the slug of the canonical
one. Search renders the canonical entry as the primary card with a "N similar
alternates" affordance. A plugin-bundled skill can point at a standalone canonical
or vice versa.
