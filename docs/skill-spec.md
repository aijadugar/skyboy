# Skyboy Skill Spec (v2)

The canonical format a skyboy.in skill package follows. This is the portable
Anthropic Agent Skills structure, extended with a skyboy-specific metadata
sidecar so we never pollute the standard format with our own fields.

v2 exists so the catalog scales from 4 skills to hundreds of thousands with
zero ambiguity: one name per skill, one authority sidecar, one compact index
record, and a display contract the site, CLI, and MCP all honor.

## 1. Identity: scoped IDs

Every skill has exactly one `id`:

- Curated Skyboy skills: a bare slug, e.g. `anti-slop-landing`.
- Everything else (company official, open source, user-uploaded): `@owner/slug`
  where owner is the GitHub org or user handle, e.g. `@vercel/nextjs-plugin`.

The bare slug space is reserved for Skyboy's own catalog. Community and vendor
skills are structurally collision-free because the owner is part of the ID.

The `slug` is always the last segment of the `id` and MUST equal the folder
name. There is no separate display name: the slug is the name. CI enforces
`frontmatter.name == folder-name == id-slug`.

### Folder layout with owners

```
skills/<category>/<slug>/                      # Skyboy-curated (bare slug)
skills/<category>/@<owner>/<slug>/             # vendor or community (scoped)
```

Example:

```
skills/coding/nextjs-app-router-conventions/           # skyboy
skills/coding/@vercel/nextjs-plugin/                   # vendor
skills/writing/@octocat/my-style-guide/                # community
```

## 2. Skill package layout

```
skill-name/
  SKILL.md          # REQUIRED - YAML frontmatter + markdown instructions
  metadata.json     # REQUIRED - the one skyboy sidecar (§4)
  meta.json         # generated - per-skill detail shard for on-demand fetch (§6)
  scripts/          # optional - executable helpers (python/js/bash)
  references/       # optional - docs loaded on demand (progressive disclosure)
  assets/           # optional - templates, boilerplate, static files
```

The two required files are `SKILL.md` and `metadata.json`. Everything else is
optional. `meta.json` is generated by `scripts/export-catalog.ts`; never
hand-edit it.

### `SKILL.md` frontmatter (v2)

```yaml
---
name: nextjs-app-router-conventions
description: Use when scaffolding or reviewing Next.js App Router projects. Enforces routing, data-fetching, and cache discipline.
license: MIT
---
```

Rules:

- `name` MUST equal the folder slug (CI-enforced). One name, ever.
- `description` MUST be at most 160 characters (CI-enforced). Sentence 1 is the
  trigger ("Use when..."), sentence 2 is optional. No marketing, no feature
  lists. Description quality is the single highest-leverage field in the whole
  schema: it is what agents scan cheaply (dozens of tokens) before deciding to
  load the full body, and it is the only long text shown in cards and search.
- `license` is recommended in frontmatter; the authoritative copy lives in
  `metadata.json` and CI cross-checks them.
- `compatible_agents` is NOT frontmatter. Agents do not declare who they are;
  Skyboy classifies in `metadata.json`. Frontmatter stays exactly what a
  portable agent expects.

## 3. `SKILL.md` is the agent surface, `metadata.json` is the Skyboy surface

The SKILL.md is the portable artifact. An agent that never hears of Skyboy can
consume a skill folder directly. Everything Skyboy-specific lives in
`metadata.json` and nowhere else. No Skyboy fields ever appear inside SKILL.md.

## 4. `metadata.json` schema (v2)

```json
{
  "id": "@vercel/nextjs-plugin",
  "category": "coding/frontend",
  "tags": ["nextjs", "app-router", "react"],
  "compatible_agents": ["claude-code", "cursor", "gemini-cli"],
  "license": "MIT",
  "author": "vercel",
  "version": "1.0.0",
  "origin": "vendor",
  "verified": false,
  "upstream_repo": "https://github.com/vercel/nextjs-plugins",
  "canonical_of": null,
  "permissions": {
    "network": false,
    "filesystem_write_outside_target": false,
    "shell_exec": false,
    "env_read": [],
    "generated_by": "generate-manifest.ts@1.0.0",
    "generated_at": "2026-09-08T00:00:00Z"
  }
}
```

### Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | yes | Bare slug (Skyboy) or `@owner/slug` (everything else). Last segment = folder name. |
| `category` | string | yes | Exactly one primary category from the taxonomy tree. |
| `tags` | array | yes | Up to 3 tags. CI enforces the cap. |
| `compatible_agents` | array | yes | Agent slugs the skill is known to work with. Lives here only (v1 also had frontmatter; that is gone). |
| `license` | string | yes | `MIT` default; CI fails on absence; must match SKILL.md frontmatter when present there. |
| `author` | string | yes | GitHub handle or org. |
| `version` | string | yes | Semver. |
| `origin` | string | yes | `skyboy` \| `vendor` \| `community`. Replaces v1 `source_type`. |
| `verified` | boolean | yes | `false` until maintainer review. Only meaningful for `origin: community`. |
| `upstream_repo` | string | when vendor | Required for `origin: vendor`, the source of truth. |
| `canonical_of` | string/null | yes | `null` for canonical; else the ID this entry duplicates (§7). |
| `permissions` | object | generated | Machine-generated; must not be hand-edited (§5). |

### Origin model (replaces badge + sourceType + verified soup)

Two fields, `origin` and `verified`, encode everything. The displayed badge is
DERIVED, stored nowhere:

| origin | verified | badge shown |
|---|---|---|
| `skyboy` | (ignored) | `official` |
| `vendor` | (ignored) | `vendor` |
| `community` | `true` | `verified` |
| `community` | `false` | `community` |

Vendor-official is never a stronger trust signal than reviewed (§3.2 of the
build brief): `vendor` means "published by the named company", not "reviewed by
skyboy".

## 5. Permissions manifest contract

`permissions` is machine-generated by `scripts/generate-manifest.ts` via static
analysis of any bundled scripts. It is a **disclosure, not a gate**: a skill
that needs network access or shell exec is fine, it just has to say so.

| Key | Type | Meaning |
|---|---|---|
| `network` | boolean | Any outbound HTTP/socket call in a bundled script. |
| `filesystem_write_outside_target` | boolean | Writes beyond the skill's own folder or the agent's declared target directory. |
| `shell_exec` | boolean | `exec`/`spawn`/`eval`/subprocess calls in a bundled script. |
| `env_read` | array | `process.env` / `os.environ` access, esp. secret-named (`*_KEY`, `*_TOKEN`, `*_SECRET`). |
| `generated_by` | string | The tool + version that produced it. |
| `generated_at` | timestamp | When it was regenerated. |

**Rule:** CI fails the build only when a script does something **undisclosed**
relative to what the contributor's PR description said the skill does.

Permissions detail is NOT in the catalog index. It is read from
`metadata.json` / `meta.json` when a skill's detail page or `get_skill` is
opened.

## 6. Three layers of representation

| Layer | File | Who consumes it | Carries |
|---|---|---|---|
| Agent surface | `SKILL.md` | any agent | name, description, instructions |
| Authority sidecar | `metadata.json` | CI, site detail page, MCP `get_skill` | full v2 schema above |
| Index record | `catalog.json` + per-skill `meta.json` | site cards/search, CLI search, MCP `search_skills` | compact display fields + hash (below) |

### `meta.json` (generated per-skill detail shard)

Written by `scripts/export-catalog.ts` into each skill folder. It is the
on-demand fetch target when a consumer needs more than the index record. It
contains the full v2 metadata plus the content hash and the SKILL.md raw URL.

### Index record shape (v2 catalog.json entries)

```json
{
  "id": "@vercel/nextjs-plugin",
  "d": "Use when scaffolding or reviewing Next.js App Router projects.",
  "c": "coding/frontend",
  "t": ["nextjs", "app-router"],
  "a": ["claude-code", "cursor"],
  "v": "1.0.0",
  "h": "9f2c1a4b8e7d3c05",
  "o": "vendor",
  "y": true,
  "p": "skills/coding/@vercel/nextjs-plugin"
}
```

| Key | Meaning |
|---|---|
| `id` | scoped ID |
| `d` | description (the 160-char display line) |
| `c` | category |
| `t` | tags |
| `a` | compatible agents |
| `v` | version |
| `h` | 16-hex prefix of sha256 over the skill folder contents |
| `o` | origin: `skyboy` \| `vendor` \| `community` |
| `y` | verified (boolean) |
| `p` | repo-relative folder path |

Roughly 200 bytes per skill. Badge is derived from `o` + `y` at render time.
License, author, upstream repo, permissions, canonical_of are NOT in the index;
fetch `meta.json` for them.

### Content hash

`h` is computed by `export-catalog.ts` over every file in the skill folder
(sorted by relative path, hash of concatenated `rel\0size\0bytes`). It powers:
- `check_updates`: hash comparison instead of trusting hand-written semver,
- immutable caching of raw URLs,
- duplicate detection without fetching bodies.

## 7. Content types

A catalog entry is either a standalone **Skill** (this spec) or a **Plugin**:
a bundle of `commands/`, `agents/`, `hooks/`, one or more `skills/`, and
optionally an `.mcp.json`. Plugins are indexed + linked back to the vendor repo
as the source of truth (never vendor-copied), and carry the `vendor` badge. The
Skill-vs-Plugin distinction is a **search facet**, not a different underlying
format.

## 8. Deduplication / canonical version

`canonical_of` points a duplicate/alternate entry at the ID of the canonical
one. Search renders the canonical entry as the primary card with a "N similar
alternates" affordance. A plugin-bundled skill can point at a standalone
canonical or vice versa. The content hash makes "same content" provable without
fetching either body.

## 9. Display contract (UI)

A card shows exactly five things plus the permissions row: **name, description,
category, badge, version**. Explanatory prose lives in `/docs`, stated once per
page type, never per skill. Design tokens: hairline borders `#c9c9c6`, pen-blue
accents `#2724d1` on strokes only, zero em-dashes in rendered text.
